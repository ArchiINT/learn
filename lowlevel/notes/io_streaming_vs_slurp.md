# Чтение данных: поток, slurp или mmap

Конспект по мотивам `01_c_foundations/const_01.c` (подсчёт байт в потоке).

Вопрос, из которого вырос конспект: *«а нельзя просто через `malloc` выделять память,
пока не поместится всё?»* — можно, но почти всегда не нужно. Разбор ниже.

---

## Задача

Есть вход неизвестного размера (файл, пайп, устройство, дамп памяти).
Надо его обработать. Вопрос: **сколько памяти выделять и когда.**

Три стратегии:

| стратегия | память | когда применять |
|---|---|---|
| **поток** (streaming) | константа | один проход, локальная обработка ← *чаще всего* |
| **slurp** (целиком в heap) | O(размера входа) | нужен random access, размер известен и мал |
| **mmap** | виртуально O(n), физически — только тронутые страницы | большие файлы + random access |

---

## Почему НЕ slurp — на измеренном примере

`const_01.c` в промежуточной версии читал один буфер на 4096 и молча обрезал вход:

```
./const_01 < /bin/ls   ->  output: 0
```

Проверка независимыми средствами:

```sh
head -c 4096 /bin/ls | tr -d -c '1' | wc -c   #   0   <- что увидела программа
tr -d -c '1' < /bin/ls | wc -c                # 990   <- сколько есть на самом деле
stat -c %s /bin/ls                            # 166640
```

Прочитано 4096 из 166640 байт = **2.5% файла**. Ответ `0` вместо `990`,
**без падения и без единого предупреждения**.

> **Железное правило:** молчаливый неверный ответ хуже краха.
> Крах виден сразу. Неверное число уходит в отчёт.

Для security-инструмента это означает «просканировал прошивку, ключей не нашёл»
при том, что ключ лежал на 5-м килобайте.

### Причины против slurp

**1. Алгоритму не нужна вся память.**
`count_byte` смотрит на `buf[i]`, увеличивает счётчик, забывает. Нужен один байт за раз.
Держать 166 КБ для задачи с O(1) по памяти — расточительство.

**2. У потока нет размера.**
Чтобы выделить заранее, надо знать сколько. Для пайпа это **невозможно в принципе**:

```sh
cat /dev/urandom | ./const_01      # бесконечный вход
./const_01 < /dev/sda              # 500 ГБ
dmesg | ./const_01                 # размер заранее неизвестен
```

`fstat()` на обычном файле даст `st_size`, **на пайпе — нет** (там нечего спрашивать).
Как только утилита должна работать в пайпе — путь «узнать размер и выделить» закрыт.

**3. Рост через `realloc` = копирование.**
Удвоение буфера копирует всё накопленное; в момент `realloc` в памяти живут
и старый, и новый блок → **пик потребления 2×**. (Подробнее: `realloc_dynamic_arrays.md`.)

**4. Размер входа контролирует не ты.**
Если инструмент выделяет память по размеру входа — противник подсовывает файл на 100 ГБ
и твой сканер убивает OOM-killer. Утилита анализа, которую можно положить её же
входными данными, — плохая утилита.
Поток держит потребление **константным и предсказуемым** независимо от входа.

## Поток: каркас

```c
unsigned char buf[4096];
unsigned long long total = 0;          /* накопитель — см. раздел о типах */
size_t n;

while ((n = fread(buf, 1, sizeof(buf), stdin)) > 0) {
    total += count_byte(buf, n, target);
}
if (ferror(stdin)) { /* ошибка чтения, а не конец данных */ }
```

Буфер становится **скользящим окном** по потоку. Потребление памяти — 4096 байт
на любом входе, от пустого до бесконечного.

Обрати внимание: `count_byte(const unsigned char *buf, size_t len, ...)` для этого
**не меняется**. Она не знает и не должна знать, откуда взялся кусок — из массива,
из файла, из сокета, из `/proc/<pid>/mem`. Вот практическая польза чистой сигнатуры
«указатель + длина».

## capacity vs length

Два разных числа, которые нельзя путать:

```c
sizeof(buf)   /* 4096 — ВМЕСТИМОСТЬ (capacity) */
n             /* сколько байт РЕАЛЬНО пришло (length) */
```

- в `fread` третьим аргументом → **capacity** (сколько максимум можно принять)
- в обработку → **length** (сколько реально есть)

Передать `sizeof(buf)` вместо `n` в обработчик = читать неинициализированный мусор
за концом данных. Программа не упадёт, выдаст правдоподобное число, и оно будет врать.

> **Железное правило:** буфер знает свою вместимость, но не свою наполненность.
> Длину обязан передавать тот, кто читал.

Это та же мысль, что `size` vs `capacity` в векторе (`realloc_dynamic_arrays.md`),
и тот же корень, что у всего класса buffer overflow: **указатель не знает своей длины.**

## Почему длина — отдельный параметр

```c
unsigned char arr[16];
sizeof(arr)   /* 16 — размер в типе, компилятор знает */

unsigned char *p = arr;
sizeof(p)     /* 8 — размер указателя   */
sizeof(*p)    /* 1 — размер элемента    */
```

При передаче в функцию массив **вырождается в указатель** (*array decay*) — знание
длины теряется на границе вызова. Поэтому `memcmp`, `memcpy`, `read`, `recv`, `fread`
все берут указатель **и** размер. Иначе никак.

При потоковом чтении длина вообще известна только в рантайме: никакой компилятор
не знает заранее, сколько байт пришлёт `stdin`.

И отдельно: **в бинарных данных нет терминатора.** `0x00` — полноправный байт данных,
а не конец. Приём «длина минус один» со строк на сырые байты **не переносится**.

## `fread` vs `read()`: короткие чтения

Проверено экспериментом (данные приходят двумя порциями с паузой):

```sh
( printf 'abc'; sleep 1; printf 'def' ) | ./prog
```

```
fread(b,1,4096,stdin)  ->  6,  feof=1     # дождался всего
read(0, b, 4096)       ->  3              # вернул что было доступно сразу
```

- **`fread`** крутит цикл внутри себя. Возвращает меньше запрошенного
  **только при EOF или ошибке**. Поэтому короткий возврат = «поток кончился»
  (или сломался) — и надо различать через `feof()` / `ferror()`.
- **`read()`** (сырой syscall) имеет право вернуть **меньше**, чем попросили,
  при том что данные не кончились. Это *partial read*, нормальное поведение
  для пайпов, сокетов, терминалов.

Классический баг: написать `read(fd, buf, 100)` и считать, что пришло 100 байт.
Пришло 30 → «прочитал половину пакета и решил, что это всё».
Лечится циклом до набора нужного количества.

Отсюда же видно, зачем `ferror`: `fread` вернул 0 либо потому что данные кончились,
либо потому что произошла ошибка чтения. По самому нулю их не отличить.
`man 3 fread`, `man 3 ferror`, `man 2 read`.

## Подводный камень потока: границы порций

Для подсчёта **одного байта** границы безвредны — байт целиком в одной из порций.

Но при поиске **последовательности** совпадение может разорваться по границе:

```
порция 1: [ ...........................  S E ]
порция 2: [ C R E T  ..........................]
                 ^
      искали "SECRET" — в обеих порциях нет целого совпадения
```

Инструмент скажет «не найдено», и ему поверят. На этом ошибаются в реальных сканерах.

**Лечение — перекрытие:** переносить последние `pattern_len - 1` байт предыдущей
порции в начало следующей.

Прямо относится к `06_security/S1_memory/`: поиск секрета через `memmem` по дампу кучи.
Если читать регион порциями без перекрытия — секрет на границе будет пропущен.

## Когда slurp действительно правильный

- нужен **произвольный доступ** (прыгать по смещениям туда-обратно)
- нужно **несколько проходов** по одним данным
- структуры растянуты на произвольное расстояние (заголовок в начале ссылается на конец)
- размер **известен и ограничен**

Разбор ELF/прошивки — именно такой случай: секции ссылаются друг на друга по смещениям.

Но тогда правильный инструмент — не `malloc` + `read`, а **`mmap`**:
файл отображается в адресное пространство, обращение идёт как к обычному массиву,
а физически в RAM попадают только тронутые страницы — ядро подгружает по требованию.
Образ на 8 ГБ «открывается» мгновенно и не ест 8 ГБ.

→ Phase 3, пункт 5. Для разбора прошивок (S2) это рабочая лошадка.

## Выбор: шпаргалка

```
Нужен произвольный доступ / несколько проходов?
├─ нет ──→ ПОТОК  (fread/read в цикле, фиксированный буфер)
└─ да ──┬→ размер большой или неизвестен ──→ MMAP
        └→ размер мал и известен ──────────→ SLURP (malloc + чтение)
```

При сомнении — поток. Переделать поток в slurp легко, обратно — тяжело.

## Упражнения

1. Переделать `const_01.c` на цикл. Контроль: `./const_01 < /bin/ls` → **990**.
2. Добавить `ferror(stdin)` и отличить «данные кончились» от «ошибка чтения».
   Проверить на каталоге — `read()` на каталоге возвращает `EISDIR`:

   ```
   ./prog < /home/vi/learn/lowlevel
   fread вернул: 0,  feof=0 ferror=1      <- ноль, но данные НЕ кончились
   ```

   Сравни с пустым вводом: там тоже `0`, но `feof=1, ferror=0`.
   По самому нулю эти две ситуации неотличимы — только через `feof`/`ferror`.
3. Тип накопителя: `count_byte` возвращает `int`. Файл на 3 ГБ нулей, ищем `0x00` →
   знаковое переполнение = **UB**, `-fsanitize=undefined` это покажет. Подобрать тип.
4. Повторить эксперимент с `read()` vs `fread` своими руками — убедиться в разнице.
5. (на будущее, Phase 2) Реализовать `my_fread` поверх сырого `read()` — станет видно,
   откуда взялось разделение `(size, nmemb)` и что делает буферизация stdio.
