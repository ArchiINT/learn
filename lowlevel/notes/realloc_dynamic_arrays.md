Конспект по мотивам `01_c_foundations/memory_02.c` (vector).

## Паттерн: динамический массив (vector)

Структура — это **пульт управления**, данные лежат отдельно, в куче:

```
СТЕК:                             КУЧА:
┌─────────────────┐              ┌────┬────┬────┬────┐
│ Vector          │              │ 10 │ 20 │ 30 │ ?? │
│  data ──────────┼─────────────→└────┴────┴────┴────┘
│  size = 3       │
│  capacity = 4   │
└─────────────────┘
```

- `capacity` — сколько элементов **влезает** в выделенный блок
- `size` — сколько **реально лежит**
- когда `size == capacity` и нужен push → realloc в **2 раза** больше

Почему в 2 раза, а не +1: realloc дорогой (может копировать весь блок).
Удвоение даёт ~10 реаллокаций на 1000 пушей вместо 1000.

Так устроены `std::vector` (C++), `list` (Python), массивы JS.

## Единицы измерения: элементы vs байты

**Железное правило:**

- `size` и `capacity` — всегда **в элементах** (штуках)
- байты появляются **только** внутри `calloc`/`realloc`: `количество * sizeof(тип)`

Типичные ошибки:

```c
vec->size += sizeof(int);          // НЕТ: добавил 1 элемент → size++
vec->capacity = sizeof(int);       // НЕТ: capacity = количество элементов
realloc(p, sizeof(cap * 2));       // НЕТ: sizeof(выражение) = размер ТИПА (8),
                                   //      значение не вычисляется!
realloc(p, cap * 2 * sizeof(int)); // ДА
```

Компилятор молчит — для него это всё валидные числа. За единицами
следишь только ты.

## Указатель от malloc — не двигать

**`free` нужно передать ровно тот адрес, который вернул malloc.**

Почему: аллокатор хранит служебный заголовок (размер блока и т.п.)
**прямо перед** выданным адресом. `free(p)` читает `p - заголовок`.
Сдвинутый указатель → free читает мусор → порча кучи / крэш
(Valgrind: `invalid free`).

Двигать и не нужно — есть индексация:

```c
vec->data[vec->size] = value;   // а не *vec->data = value; vec->data++;
vec->size++;
```

`data[i]` — доступ за O(1): адрес вычисляется как `data + i * sizeof(int)`.
Цикл-обход нужен в связном списке, не в массиве.

То же с free: один calloc/malloc → **один** free. Цикл free был нужен
в списке (malloc на каждую ноду), здесь блок один.

```c
free(vec->data);
vec->data = NULL;   // хороший тон: free(NULL) легален и безопасен
```

## realloc: три сценария

`realloc(old_ptr, new_size)`:

| Сценарий | Что происходит | Что возвращает |
|---|---|---|
| Удача | за блоком есть место — расширил на месте | **тот же адрес** |
| Переезд | места нет — выделил новый блок, **скопировал** данные, освободил старый | **новый адрес** |
| Провал | памяти нигде нет | **NULL**, старый блок **жив и валиден** |

### Паттерн с tmp (обязательный)

```c
// ПЛОХО: если realloc вернул NULL, единственный указатель
// на живой старый блок перезаписан → утечка, данные потеряны
vec->data = realloc(vec->data, new_bytes);

// ПРАВИЛЬНО
int *tmp = realloc(vec->data, new_bytes);
if (tmp == NULL) {
    return 1;          // vec->data цел, данные на месте
}
vec->data = tmp;
```

Провал realloc не воспроизводится на дев-машине (память не кончается) —
и обязательно стреляет в проде. Такие ошибки отличают джуна от мидла.

### После переезда старый указатель мёртв

realloc при переезде сам освобождает старый блок. Старый адрес больше
**не принадлежит тебе** — поэтому результат realloc всегда присваивают
обратно.

## Dangling pointer и use-after-free

- **Dangling pointer** — указатель на уже освобождённую память
- **Use-after-free (UAF)** — обращение через него

Коварство: free **не затирает** байты (медленно), он лишь помечает блок
свободным. Старые данные физически лежат на месте, и чтение через
dangling pointer часто «работает»… пока аллокатор не выдаст эту память
следующему malloc — тогда читаешь/пишешь чужое.

- Баг **плавающий**: тесты зелёные, ломается в проде под нагрузкой
- Valgrind ловит сразу: `Invalid read` / `Invalid write`
- Security: UAF — одна из самых эксплуатируемых категорий уязвимостей
  (~половина CVE в браузерах). В плане — фаза S1 (heap exploitation)

## Разбор реального бага: `realloc(): invalid next size`

Случился в моём же `memory_02.c` — записываю по горячим следам.

### Симптом

```
$ ./memory_02
realloc(): invalid next size
Aborted (exit code 134)
```

Крэш внутри realloc — но realloc не виноват. Он **детектор**, не преступник.

### Причина

```c
vec->capazity = sizeof(vec->data);   // sizeof(указателя) = 8. ВСЕГДА 8
```

`sizeof` от указателя — размер самого указателя (8 байт на 64-бит),
а не того, на что он указывает. calloc выделил **4** элемента,
а в capacity записалось **8** → структура думает, что места больше,
чем есть.

### Цепочка до крэша

1. Пуши 0–3 — в блок, нормально
2. Пуш 4: `size == capacity` → `4 == 8` → false, realloc не сработал.
   Запись в `data[4]` — **за границей блока** (heap overflow)
3. Пуши 5–7 — дальше за границу. Сразу за блоком лежит **заголовок
   следующего чанка кучи** (метаданные аллокатора) — он затёрт
4. Пуш 8: `8 == 8`, вызывается realloc → он читает метаданные,
   видит мусор → glibc убивает процесс: `invalid next size`

### Уроки

- **Место крэша ≠ место бага.** Порча кучи проявляется позже — там,
  где аллокатор в следующий раз заглянет в свои метаданные
- Крэш внутри malloc/realloc/free = «кто-то ДО этого писал мимо
  памяти» → сразу Valgrind, смотреть **первую** `Invalid write`:

```
Invalid write of size 4
   at vec_push (memory_02.c:50)              ← кто писал мимо
 Address ... is 0 bytes after a block of size 16 alloc'd
   at calloc (vec_create, memory_02.c:32)    ← какой блок переполнен
```

- Числа, которые обязаны совпадать (аргумент calloc и capacity),
  не должны быть написаны руками в двух местах — вынести в константу
- **Security (S1):** heap overflow с порчей метаданных чанка — базовый
  примитив эксплуатации кучи. Здесь glibc заметил и убил процесс;
  задача атакующего — затереть метаданные так, чтобы проверки прошли

## Контракт vector (для реализации в memory_02.c)

```c
typedef struct {
    int *data;
    size_t size;      // элементов лежит
    size_t capacity;  // элементов влезает
} Vector;

int  vec_create(Vector *vec);           // calloc(4) в data, size=0, capacity=4
int  vec_push(Vector *vec, int value);  // size==capacity → realloc x2 (через tmp!)
                                        // data[size] = value; size++
int  vec_get(Vector *vec, int index);   // проверить index < size; вернуть data[index]
void vec_free(Vector *vec);             // free(data) один раз; data = NULL
```

Проверка: 20 пушей (capacity вырастет несколько раз), печать через
vec_get, `valgrind` — ноль утечек.
