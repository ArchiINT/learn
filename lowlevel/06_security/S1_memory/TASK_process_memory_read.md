# Задание: чтение памяти чужого процесса (process memory introspection)

**Трек:** Phase 6 — Embedded Security / S1 (работа с памятью процессов)
**Связано с:** динамические массивы (`malloc`), указатели — то, что учим сейчас в Phase 1.
**Суть:** одна программа принимает ввод пользователя, вторая — читает этот ввод прямо из памяти первой. Простой reverse engineering.

---

## Как это вообще возможно

В Linux память каждого процесса доступна через псевдо-ФС `/proc`. Ядро подставляет два файла:

- `/proc/<pid>/maps` — текстовая карта памяти процесса: адреса регионов, права (`r/w/x`), что это (`[heap]`, `[stack]`, библиотеки).
- `/proc/<pid>/mem` — «файл», где **смещение = виртуальный адрес**. Чтобы прочитать байт по адресу `0x5555...`, делаешь `lseek` на это смещение и `read`.

Вся «магия» на этом. Никакого взлома — ядро само экспонирует память. Главный вывод: **память НЕ приватна по умолчанию** между процессами одного пользователя. Отсюда и урок безопасности.

---

## Важно: защита Yama ptrace_scope

Проверить текущее значение:

```
cat /proc/sys/kernel/yama/ptrace_scope
```

- `0` — можно читать память любого своего процесса. Задание сработает сразу.
- `1` (частый дефолт) — только память **потомков** (child) или через `sudo`.

Если стоит `1`:
- запускай читалку через `sudo`, **или**
- временно ослабь: `echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope`

Урок реального мира: `ptrace_scope` придумали именно чтобы малварь не воровала пароли/ключи из памяти других процессов.

## План (в два этапа)

### Программа A — «жертва» (пишу сам, знаний хватает)
1. Просит пользователя ввести строку (например «пароль»).
2. Кладёт её в буфер через `malloc` (это наш динамический массив).
3. Печатает свой PID (`getpid()`) — чтобы читалка знала, к кому подключаться.
4. Зависает в `while(1)` / `getchar()`, чтобы процесс не завершился и память осталась жива.

### Программа B — «читалка» (новое)
1. Принимает PID аргументом (`argv[1]`).
2. Открывает `/proc/<pid>/mem`.
3. Читает секрет и печатает его.

Этап B — по нарастающей сложности:
- **Лёгкий:** программа A дополнительно печатает адрес буфера (`printf("%p\n", buf)`). B прыгает прямо на этот адрес — учим сам механизм чтения.
- **Хардкорный (настоящий RE):** адрес неизвестен. B читает `/proc/<pid>/maps`, находит регион `[heap]` и **сканирует** его, ища знакомую строку.

## Non-guessable синтаксис (дано заранее — сам не выведешь)

Формат строки в `/proc/<pid>/maps`:
```
5555555592a0-5555555593c0 rw-p 00000000 00:00 0    [heap]
^начало       ^конец      ^права           ^что это
```
Адреса в hex: начало и конец региона.

Чтение по адресу из `/proc/<pid>/mem` (адрес 64-битный → нужен `off_t` и `lseek`):
```c
int fd = open(path, O_RDONLY);            // path = "/proc/1234/mem"
lseek(fd, (off_t)target_addr, SEEK_SET);  // прыгаем на виртуальный адрес
read(fd, buffer, n);                       // читаем n байт
```
`off_t` — 64-битный тип для смещений в файле. На x86_64 он и так 64-битный
(при желании гарантировать: `#define _FILE_OFFSET_BITS 64` до include-ов).

## Быстрая проверка БЕЗ своего кода (готовые тулзы)

Идея: прежде чем писать `reader.c`, можно прочитать память жертвы готовыми
инструментами. Механизм везде один и тот же: **open → lseek на адрес → read**.
Разные тулзы просто делают эти три шага за тебя.

### Ключевой факт про `/proc/<pid>/mem`
**Смещение в файле = виртуальный адрес.** Чтобы прочитать байт по адресу
`0x5642e8da2010`, надо спозиционироваться (`lseek`/seek) ровно на это число и читать.
Файл НЕ читается «с начала» — это окно, где валидны только реально отображённые
адреса.

Поэтому `cat /proc/<pid>/mem` падает:
- без `sudo` → `Permission denied` (защита `ptrace_scope = 1`);
- с `sudo` → `Input/output error` (EIO): `cat` читает со смещения `0`, а адрес
  `0x0` в процессе не отображён → ядро отдаёт EIO. `cat` не умеет прыгать на адрес.

### Метод 1 — `xxd` (ближе всего к reader.c) ✅ проверено, работает
```bash
sudo xxd -s 0x5642e8da2010 -l 64 /proc/<pid>/mem
```
- `-s 0x…` — seek = наш `lseek` на виртуальный адрес (принимает hex с `0x`);
- `-l 64` — length, сколько байт прочитать;
- вывод: hex-дамп + ASCII-колонка справа → там видно введённый секрет.
- `xxd` сам делает `open` + `lseek` + `read` — это reader.c в одну строку.

### Метод 2 — `dd`
```bash
sudo dd if=/proc/<pid>/mem bs=1 skip=$((0x5642e8da2010)) count=64 iflag=skip_bytes 2>/dev/null | xxd
```
- `skip=$((0x…))` — оболочка переводит hex→dec, это offset;
- `iflag=skip_bytes` — считать `skip` в байтах (и сделать `lseek`), а не в блоках.

### Метод 3 — `gdb` (RE-стандарт, живой процесс)
```bash
sudo gdb -p <pid>
(gdb) x/s 0x5642e8da2010   # examine as string по адресу
(gdb) detach               # отцепиться, НЕ убив жертву
(gdb) quit
```

### Почему всё под sudo
`ptrace_scope = 1`: читать память чужого (не-потомка) процесса того же юзера
нельзя без `CAP_SYS_PTRACE`. `sudo` даёт эту привилегию. Это и есть защита от
воровства секретов из памяти — тот самый урок безопасности.
