## 1. Что такое архитектура процессора (ISA)

Процессор — исполнитель, который понимает команды. Вопрос: **на каком языке** ему эти команды давать?

**ISA (Instruction Set Architecture)** — это «язык команд» процессора. Он описывает:
- какие команды процессор понимает (`add`, `mov`, `load`…),
- какие у него регистры (внутренние ячейки для чисел),
- как он работает с памятью.

> ISA — это **контракт** между железом и программой. Программа, скомпилированная под один язык команд, **не запустится** на процессоре, который говорит на другом.

Именно поэтому программа с ноутбука (x86) не заработает на ESP32 или Raspberry Pi. Разные языки.

**Аналогия:** дать китайцу текст на китайском — прочитает. Кинуть тот же текст русскому (ESP32) — не поймёт ни слова.

## 2. Три языка: x86, ARM, RISC-V

| | **x86** | **ARM** | **RISC-V** |
|---|---|---|---|
| Тип | CISC (сложный) | RISC (простой) | RISC (простой) |
| Где живёт | ПК, ноутбуки, серверы | телефоны, планшеты, Apple M-чипы, STM32, часть ESP32 | новьё, дешёвый IoT, ESP32-C, Китай |
| Энергопотребление | высокое | низкое | низкое |
| Открытость | закрыт (Intel/AMD) | по платной лицензии | **открыт и бесплатен** |
| Год рождения | 1978 | 1985 | 2010 |

**x86** — «старый богатый город». Почти 50 лет, обратная совместимость слоями, прожорлив. Делают Intel и AMD.

**ARM** — «энергоэффективный чемпион». Сама ARM **не делает чипы** — она продаёт **лицензию на архитектуру**. Apple, Qualcomm, STMicroelectronics берут дизайн и строят свои чипы.

**RISC-V** — «свободный новичок». Открытый стандарт, как Linux в мире процессоров: **строй свой чип бесплатно, никому не плати**. Уточнение: открыта сама **спецификация**; конкретный чип на RISC-V фирма может сделать закрытым и продавать.

## 3. CISC vs RISC

Это ядро различия. И тут легко попасть в ловушку.

- **CISC** (x86) — **мало мощных команд**. Одна команда может «сходить в память, взять число и прибавить» — всё за один приказ.
- **RISC** (ARM, RISC-V) — **много простых команд**. То же действие разбивается: «загрузи из памяти» → «сложи регистры» → «сохрани».

### ⚠️ Ловушка: RISC ≠ «медленный»

Простые команды **не значит медленно**. Наоборот, часто быстрее и всегда экономичнее:
- простые команды процессору **легче предсказывать и параллелить** (конвейер, несколько за такт);
- современный x86 **внутри сам разбивает** свои сложные команды на простые микро-операции — то есть внутри работает почти как RISC.

Доказательство: Apple M1/M2/M3 — это **ARM (RISC)**, и они обгоняют многие x86, потребляя в разы меньше энергии.

> Правильная формулировка: CISC vs RISC — это **«сложные команды vs простые команды»**, а НЕ «быстрый vs медленный».

## 4. Один C — два ассемблера

Исходник:

```c
int add_from_memory(int *p, int b) {
    return *p + b;   // взять число из памяти по адресу p, прибавить b
}
```

### x86 (реальный вывод gcc, CISC):

```asm
mov  eax, esi                 ; положить b в регистр-результат
add  eax, DWORD PTR [rdi]     ; ★ ОДНА команда: сходить в память И прибавить
ret
```

Строка `add eax, [rdi]` делает **две вещи сразу**: лезет в память по адресу `rdi` и складывает. Квадратные скобки `[...]` = «сходи в память по адресу» (это `*p` из C).

### ARM (тот же C, RISC):

```asm
ldr  w2, [x0]        ; ★ шаг 1: ТОЛЬКО загрузить число из памяти
add  w0, w2, w1      ;   шаг 2: ТОЛЬКО сложить два регистра
ret
```

Здесь то же действие — **два шага**: сначала `ldr` (load), потом `add`.

### Что запомнить для реверса

- **Регистры называются по-разному**: x86 → `rax / rdi / rsi / eax`, ARM → `x0 / x1 / w0 / w2`. Увидел `x0` в Ghidra → это ARM. Увидел `rax` → это x86.
- **`ldr` / `str` (load/store)** — фирменный признак RISC. В ARM арифметика идёт **только между регистрами**, а память трогается **только** через load/store. Это называется **load/store архитектура**. В x86 арифметика может лезть в память напрямую.
- Квадратные скобки `[...]` в обоих языках = разыменование (`*` из C).

Команда для проверки самому:
```bash
gcc -O1 -S -masm=intel demo.c -o demo.s    # x86
# для ARM понадобится кросс-компилятор, напр. aarch64-linux-gnu-gcc
```

## 5. Бренд ≠ архитектура

Частая путаница. **Бренд** — это торговое имя (как «iPhone»). **Архитектура** — это язык команд.

- **Ryzen** — это бренд процессоров **AMD**, и **все они x86-64**. ARM-процессоров под именем Ryzen не существует.
- Историческая деталь: AMD **пробовала** ARM (серверный Opteron A1100 «Seattle», ~2016; проект ядра «K12»), но **не под брендом Ryzen**. Ryzen с самого начала (2017) и по сей день — только x86.

| Бренд / кто делает | Архитектура |
|---|---|
| AMD Ryzen | x86-64 |
| Intel Core (i5, i7…) | x86-64 |
| Apple M1/M2/M3 | ARM |
| Qualcomm Snapdragon | ARM |
| STM32, часть ESP32 | ARM (Cortex-M) |
| ESP32-C, новые чипы | RISC-V |

**Правило навскидку:** ПК/ноутбук/сервер (Intel, AMD/Ryzen) → x86. Телефон/планшет/Mac на M-чипе/микроконтроллер → ARM (или RISC-V у новья).

## 6. Почему мир не перейдёт на ARM за один день

Apple доказала, что ARM мощный. Но переход идёт **медленно**, и вот почему.

### Причина №1 — гора уже собранного x86-софта
За 40+ лет под x86 **скомпилированы** миллионы программ, у многих **нет исходников**. Скажи «теперь только ARM» — половина софта перестанет запускаться (ARM не понимает x86-команды). Это **обратная совместимость** — главный «ров с крокодилами», защищающий x86.

### Почему у Apple получилось
Apple **контролирует весь стек**: железо (чипы M) + ОС (macOS) + магазин приложений. И сделала **Rosetta 2** — переводчик, который на лету превращает x86-команды в ARM. Мир Windows раздроблен (сотни производителей железа + Microsoft + Intel/AMD), договориться всем сразу почти невозможно. **Это бизнес-преимущество Apple, а не только техническое.**

### Причина №2 — серверы и предприятия консервативны
Правило дата-центров: «работает — не трогай». Переписывать 10–20-летний софт под ARM — риск и деньги.

### Но переход УЖЕ идёт
- **Windows on ARM** (ноутбуки на Snapdragon, со своим переводчиком),
- **серверы на ARM** (Amazon Graviton, Ampere) — дешевле и экономичнее,
- весь **мобильный мир** давно ARM.

> ARM не проигрывает технически — его тормозит гора x86-софта и раздробленность индустрии ПК. Там, где один игрок контролирует всё (Apple) или где софт новый и пересобираемый (облако), переход **уже случился**.

## 7. Два разных вида «перевода»

Ключевая идея всей темы. Постоянно путают **два независимых уровня** перевода:

### Перевод №1 — язык команд (архитектура)
`x86-машинный-код` → `ARM-машинный-код`
Делают: **Rosetta 2** (Apple), **QEMU**, **FEX-Emu**, **box64/box86**.

### Перевод №2 — язык обращений к ОС (API)
`Windows-вызовы` → `Linux-вызовы`
Делают: **Wine**, **Proton**.

> Wine и Proton **НЕ переводят архитектуру**. Они переводят только Windows→Linux, оставаясь в **том же** языке команд. Wine берёт **x86-Windows**-программу и запускает на **x86-Linux** — процессор один и тот же.

Эти два перевода можно **складывать стопкой** (см. ниже).

## 8. Совместимость на Linux

Технически на Linux переход на ARM — **самый гладкий**, потому что Linux **открыт**: почти весь софт можно **пересобрать из исходников** под любую архитектуру.

Доказательства, что Linux на ARM уже везде:
- **Raspberry Pi** — Linux на ARM,
- **Android** — ядро Linux на ARM (миллиарды устройств),
- **Amazon Graviton** — серверы Linux на ARM,
- репозитории Arch собраны и под x86, и под ARM (Arch ARM).

⚠️ Важная поправка: Apple выиграла **не потому, что macOS — Unix**. «Unix-ность» тут ни при чём. Преимущество Linux — **не родство с Mac, а открытые исходники**.

### Родной Linux-софт → ARM: легко
Есть исходники → пересобрал → работает. Один шаг.

### x86-Windows-игра → ARM-Linux: два слоя перевода
```
Windows x86 игра
      │
      ▼
[ Wine / Proton ]     ← перевод №2: Windows-вызовы → Linux-вызовы
      │
      ▼
[ FEX-Emu / box64 ]   ← перевод №1: x86-команды → ARM-команды
      │
      ▼
  ARM процессор
```
Два переводчика подряд, каждый теряет немного скорости. Именно так гоняют Windows-игры на Raspberry Pi или Mac ARM.

### x86-Windows-игра → x86-Linux (Steam Deck): один слой
Steam Deck — это **Linux на x86**. Язык команд один (x86 = x86), переводить надо **только API** (Windows→Linux через Proton). Поэтому виндовые игры идут отлично, иногда **быстрее**, чем на Windows.

## 9. Почему Mac силён в графике, но слаб в играх

Парадокс: монтаж, 3D, работа с графикой — летают; игры — тормозят.

⚠️ Поправка: видеокарта у Mac **есть** — просто **встроена в тот же чип** (интегрированный GPU), и она **мощная**. Дело не в нехватке графической мощи.

### Почему творческий софт летает
1. **Нативный код.** Final Cut, DaVinci Resolve, Blender собраны под ARM и под графический язык Apple (**Metal**). Никаких переводчиков.
2. **Единая память (unified memory).** В обычном ПК у процессора своя RAM, у видеокарты своя VRAM, и данные **копируются** туда-сюда. В Apple-чипе CPU и GPU **делят одну память** → для гигабайтных видео/3D-ассетов **ничего не надо копировать**. Огромный выигрыш.
3. **Спец-железо (аппаратные ускорители).** В чипе есть **медиа-движки** под видеокодеки (ProRes и др.) — отдельный кремний под конкретную задачу.

### Почему игры тормозят — снова два слоя перевода
Игры пишут под **DirectX** (язык Windows). Mac понимает только **Metal**. Плюс многие игры — x86-бинарники. Значит:
```
Windows x86 игра (DirectX)
        │
        ▼
[ Rosetta 2 ]   ← перевод №1: x86 → ARM
        │
        ▼
[ D3DMetal ]    ← перевод №2: DirectX → Metal
        │
        ▼
   Apple GPU
```
Два перевода подряд съедают производительность.

### Но корень — бизнес, не техника
Нативно портированные под Metal игры идут отлично. Но доля геймеров на Mac мала → разработчикам **невыгодно** портировать → замкнутый круг. У творческого софта круг обратный: профессионалы на Mac, рынок большой → вкладываются.

| | Творческий софт | Игры |
|---|---|---|
| Код | нативный ARM+Metal | часто x86+DirectX через 2 перевода |
| Память | единая — плюс для больших ассетов | плюс есть, но съедается переводом |
| Спец-железо | медиа-движки под видео | спец-ускорителей под игры нет |
| Бизнес | рынок большой → вкладываются | рынок мал → не портируют |

## 10. Графические API

**Графический API** — это **язык между игрой и видеокартой**. Игра не общается с железом напрямую (видеокарт тысячи разных). Она говорит на API готовыми командами («нарисуй треугольник», «наложи текстуру»), а **драйвер видеокарты** переводит их в команды конкретного железа. Тот же принцип абстракции, что «пишу на C, а компилятор разбирается с x86/ARM».

| API | Владелец | Где работает |
|---|---|---|
| **DirectX** (графическая часть = **Direct3D / D3D**) | Microsoft | только Windows |
| **Metal** | Apple | только Mac / iPhone |
| **OpenGL** | открытый стандарт | везде, но **старый** (с 1992), уходит |
| **Vulkan** | открытый стандарт | везде, **современный** (с 2016), главный на Linux |

- **DirectX** — набор API от Microsoft под Windows; графическая часть — **Direct3D**. «Игра на DirectX 11/12» = Direct3D. Привязан к Windows, на Linux/Mac нативно **нет**.
- **На Linux используют** OpenGL (старый, уходит) и **Vulkan** (современный, открытый, главный).

### Как виндовые игры идут на Linux — DXVK
```
Windows игра (DirectX)
        │
        ▼
[ DXVK ]   ← переводит DirectX → Vulkan
        │
        ▼
    Vulkan (родной для Linux)
        │
        ▼
   драйвер → видеокарта
```
**DXVK** входит в **Proton** (Steam). Перевод настолько хорош, что многие игры идут как на Windows или **быстрее** (Vulkan эффективнее). Здесь только **смена API** (DirectX→Vulkan), **без** смены архитектуры — игра x86 и Linux x86, язык команд один. Поэтому **Steam Deck** (Linux на x86) отлично играет в виндовые игры.

## 11. Почему это важно для embedded-security

- **Реверс прошивок (Phase S2):** STM32 = ARM, старые ПК = x86. В Ghidra придётся выбрать архитектуру — ошибёшься, получишь мусор. Уметь отличать `x0` (ARM) от `rax` (x86) — обязательно.
- **Эксплойты / переполнение буфера (Phase S1):** перезапись адреса возврата работает через регистры — в x86 это `rip/rsp`, в ARM `pc/lr/sp`. Механика похожа, детали разные.
- **Кросс-компиляция (Phase 4):** эксплойт, собранный под Ryzen-ноутбук (x86), **не подойдёт** к прошивке STM32 (ARM) — придётся кросс-компилировать.
- **Системные вызовы (Phase 2):** Wine — это гигантский слой, перехватывающий **системные вызовы Windows** и переводящий в линуксовые. Разобравшись с сисколлами, поймёшь его изнутри.

> Вывод: читать **и x86, и ARM** ассемблер — не «на выбор», а обязательный навык.

## 12. Шпаргалка

- **ISA** = язык команд процессора. Код из-под одного языка не идёт на другом.
- **x86** = CISC, ПК/серверы, Intel+AMD (Ryzen — это x86!). **ARM** = RISC, мобильники/Apple/STM32. **RISC-V** = RISC, открытый.
- **CISC vs RISC** = «сложные команды vs простые», НЕ «быстрый vs медленный».
- **RISC-признаки в асме:** регистры `x0/w0`, работа с памятью только через `ldr/str`.
- **Два перевода:** архитектура (x86→ARM: Rosetta/QEMU/box64) и API/ОС (Windows→Linux: Wine/Proton). Их **складывают стопкой**.
- **Слоёв перевода = медленнее.** Steam Deck (x86-Linux) = 1 слой. Игра на Mac ARM = 2 слоя.
- **Графические API:** DirectX (Windows), Metal (Apple), OpenGL (старый), **Vulkan** (Linux, современный). **DXVK** = DirectX→Vulkan внутри Proton.
- **Mac и графика:** силён из-за нативного кода + единой памяти + медиа-движков; слаб в играх из-за 2 слоёв перевода и малого рынка (бизнес, не железо).
