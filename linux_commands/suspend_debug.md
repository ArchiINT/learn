# Диагностика: чёрный экран после сна (NVIDIA + X11)

Разбор реального случая от 2026-08-03. Здесь важны не столько сами команды,
сколько **порядок рассуждений**: от «случилось ли событие вообще» к «что именно оно сделало».

Симптом: закрыл крышку → открыл → система жива, экран чёрный.
Гипотеза пользователя: «нужно включить nvidia-suspend сервисы и перезагрузиться».
Итог расследования: гипотеза оказалась неверной, и логи это доказали за 5 минут.

---

## Принцип: не гадай, проверяй в правильном порядке

Когда что-то «не работает», есть соблазн сразу применить совет из интернета.
Правильная последовательность другая:

1. **Событие вообще произошло?** (сервис запускался? система засыпала?)
2. **Если произошло — что оно сделало?** (читаем код того, что запустилось)
3. **Что сломалось конкретно?** (сужаем область: ядро / драйвер / X / подсветка)

На каждом шаге — команда, которая даёт факт, а не мнение.

## Шаг 1. Состояние systemd-юнитов

```sh
systemctl is-enabled nvidia-suspend.service nvidia-hibernate.service nvidia-resume.service
systemctl status nvidia-suspend.service --no-pager
```

- `is-enabled` — короткий ответ `enabled`/`disabled`. Удобно для скриптов, не нужно
  глазами искать строку в выводе `status`.
- `--no-pager` — **обязательная привычка**. Без неё systemd открывает `less`, и в
  неинтерактивном контексте (скрипт, пайп, вызов из другой программы) команда зависнет.
  То же самое актуально для `journalctl`.
- В выводе `status` смотри на строку `Loaded:` — там путь к unit-файлу. Он понадобится дальше.

Тонкость: для `Type=oneshot` сервиса `Active: inactive (dead)` — это **норма**.
Такой сервис отработал и завершился. «Не запущен» и «отработал» здесь выглядят одинаково,
поэтому по `status` нельзя судить, случился ли запуск. Нужен журнал.

## Шаг 2. Журнал — главный инструмент

### Список загрузок

```sh
journalctl --list-boots --no-pager
```

Вывод:
```
 -1 b950d12b... Mon 2026-08-03 09:00:51 CEST  Mon 2026-08-03 09:19:29 CEST
  0 92a2187c... Mon 2026-08-03 09:19:50 CEST  Mon 2026-08-03 09:22:44 CEST
```

`0` — текущая загрузка, `-1` — предыдущая, и так далее.
Это первое, что нужно смотреть при отладке проблем со сном: **интересное событие почти
всегда в прошлой загрузке**, потому что после чёрного экрана машину жёстко перезагрузили.

Работает только если журнал персистентный. Проверить:
```sh
ls -d /var/log/journal          # каталог есть → журнал переживает перезагрузку
```
Если каталога нет — журнал лежит в `/run/log/journal` (tmpfs) и стирается при ребуте.
Тогда: `sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald`.

### Поиск по журналу

```sh
journalctl -b -1 -g "PM: suspend|nvidia-suspend|Lid" --no-pager
```

- `-b -1` — только предыдущая загрузка.
- `-g PATTERN` (`--grep`) — фильтр по regex **на стороне journalctl**. Лучше, чем
  `journalctl | grep`, потому что journalctl умеет искать по сжатым архивным файлам
  журнала, не разжимая их целиком в пайп.
- Регистр: `-g` по умолчанию регистронезависим, если паттерн в нижнем регистре
  (умное поведение, как `smartcase` в vim).

### Окно по времени

```sh
journalctl -b -1 --since "09:19:00" --until "09:19:30" --no-pager
```

Когда момент сбоя уже найден — вырезаем окно вокруг него и читаем **всё подряд**, без
фильтров. Именно так находятся неожиданные вещи: в этом случае так обнаружилось, что
WiFi переподключился после пробуждения — значит система жива, и виноват только вывод.

Полезно отсеять шум:
```sh
journalctl -b -1 --since "09:19:15" --until "09:19:29" --no-pager \
  | grep -vE "bluetoothd|NetworkManager|wpa_supplicant"
```
`grep -v` — инверсия, `-E` — расширенные регулярки (чтобы работал `|` как «или»).

### Только сообщения ядра

```sh
journalctl -b -1 -k --no-pager
```
`-k` (`--dmesg`) — эквивалент `dmesg`, но с историей по загрузкам. Обычный `dmesg`
показывает только текущую загрузку и вылетает при переполнении кольцевого буфера.

### Ключевые маркеры сна в журнале

| Строка | Что означает |
|---|---|
| `systemd-logind: Lid closed.` | крышка закрыта, событие дошло до logind |
| `PM: suspend entry (s2idle)` | ядро начало засыпание, режим `s2idle` |
| `Freezing user space processes` | заморозка процессов |
| `Suspending console(s)` | последнее сообщение перед реальным сном |
| `PM: suspend exit` | ядро вернулось, resume прошёл |

Если есть `suspend entry`, но нет `suspend exit` — машина не проснулась.
Если есть оба, а экрана нет — проблема **только в выводе изображения**. Это и был наш случай.

## Шаг 3. Читай код того, что запускается

Логи показали, что `nvidia-suspend.service` отработал. Значит вопрос — что он делает.

```sh
cat /usr/lib/systemd/system/nvidia-suspend.service
```
```ini
ExecStart=/usr/bin/logger -t suspend -s "nvidia-suspend.service"
ExecStart=/usr/bin/nvidia-sleep.sh "suspend"
```

Кстати, здесь объяснилась загадочная строка в журнале `suspend[31505]: nvidia-suspend.service` —
это `logger -t suspend` (`-t` = tag, имя источника). Всегда полезно понимать, откуда
взялась каждая строка лога.

Дальше — сам скрипт:
```sh
cat /usr/bin/nvidia-sleep.sh
```
```sh
if [ ! -f /proc/driver/nvidia/suspend ]; then
    exit 0
fi
```

**Вот и разгадка.** Скрипт выходит на третьей строке, если нет файла. Проверяем:

```sh
ls -la /proc/driver/nvidia/
```

Файла `suspend` нет (есть только `suspend_depth`) → сервис ничего не делает.
Никакая перезагрузка это не изменит.

Мораль: unit-файлы в `/usr/lib/systemd/system/` и скрипты в `/usr/bin/` — это
обычный текст. Читать их быстрее, чем гуглить, что делает сервис.

## Шаг 4. Параметры модуля ядра

Почему нет файла `/proc/driver/nvidia/suspend`? Из-за параметров модуля.

```sh
cat /proc/driver/nvidia/params
```
```
PreserveVideoMemoryAllocations: 2
UseKernelSuspendNotifiers: 1
TemporaryFilePath: "/var/tmp"
```

Универсальный способ для любого модуля:
```sh
ls /sys/module/<модуль>/parameters/          # список параметров
cat /sys/module/<модуль>/parameters/<имя>    # текущее значение
```
Часть файлов там с правами `0400` (только root) — тогда `sudo cat`.

Откуда параметры берутся:
```sh
grep -r "" /etc/modprobe.d/          # конфиг администратора (приоритет выше)
grep -r "" /usr/lib/modprobe.d/      # конфиг от пакетов
cat /proc/cmdline                    # параметры из загрузчика
```

`/etc/modprobe.d/` оказался пуст, а виновник нашёлся в `/usr/lib/modprobe.d/nvidia-sleep.conf` —
файл **от самого пакета** `nvidia-utils`:
```
options nvidia NVreg_UseKernelSuspendNotifiers=1
```

Это важный урок: отсутствие твоих настроек ≠ отсутствие настроек. Дистрибутив
кладёт свои в `/usr/lib/`, и они действуют.

## Шаг 5. Что за железо

```sh
lspci | grep -iE "vga|3d|display"      # видеокарты
lspci -nn                              # с ID вендора/устройства [10de:28e1]
lsmod | grep -i nvidia                 # загруженные модули и счётчик ссылок
```

`-nn` даёт `[10de:28e1]` — числовые ID. Нужны, когда гуглишь баги: по ID находится
точная модель, по названию — каша из похожих.

В `lsmod` третья колонка — сколько всего ссылается на модуль, четвёртая — кто именно.
`nvidia_drm 167936 7` означает 7 активных пользователей — модуль занят, выгрузить не выйдет.

Находка: `lspci` показал только RTX 4050, а AMD-видеоядро числится как
`absent graphics controller` — встроенной графики нет. Значит панель висит напрямую
на NVIDIA, и запасного пути вывода изображения не существует.

## Шаг 6. Состояние дисплеев

### Уровень ядра (DRM)

```sh
ls /sys/class/drm/
grep . /sys/class/drm/card1-*/status
grep . /sys/class/drm/card1-*/enabled
```

`grep . файлы` — идиома для чтения кучи мелких файлов в `/sys` и `/proc`:
выводит `путь:содержимое` для каждого. Точка = «любой символ», то есть любая непустая строка.
Гораздо удобнее, чем `for` или `head -n -0 *`.

Что означают файлы:
- `status` — `connected` / `disconnected`: воткнут ли физически монитор
- `enabled` — включён ли вывод в текущей конфигурации
- `dpms` — состояние энергосбережения (`On`/`Off`)

Оговорка: под Xorg с проприетарным драйвером NVIDIA эти файлы часто врут, потому что
X работает мимо DRM-KMS. Сверяйся с `xrandr`.

### Уровень X

```sh
DISPLAY=:0 XAUTHORITY=/run/user/1000/lyxauth xrandr --query
```

Зачем переменные: `xrandr` — X-клиент. Из SSH или из systemd-юнита переменных окружения
нет, и он не знает, к какому серверу подключаться и чем авторизоваться.
- `DISPLAY=:0` — какой X-сервер
- `XAUTHORITY` — файл с cookie авторизации

Путь к auth-файлу не угадывают, а смотрят в командной строке процесса:
```sh
pgrep -a Xorg
# 1345 /usr/lib/Xorg :0 vt1 -auth /run/user/1000/lyxauth
```
`pgrep -a` = найти процесс + показать полную командную строку.

### Подсветка

```sh
ls -la /sys/class/backlight/
cat /sys/class/backlight/nvidia_0/{brightness,max_brightness,actual_brightness}
```

Важное различие: `brightness` — что **запросили**, `actual_brightness` — что реально
на панели. Расхождение = железо не приняло значение.

Это отдельная от modeset причина чёрного экрана: картинка может рисоваться корректно,
но подсветка выключена. Проверяется одной командой, поэтому исключать её надо рано.

## Шаг 7. Логи Xorg

```sh
ls -la ~/.local/share/xorg/
tail -30 ~/.local/share/xorg/Xorg.0.log.old
```

Современный Xorg от обычного пользователя (rootless) пишет в `~/.local/share/xorg/`,
а не в `/var/log/`. Файл `.old` — предыдущая сессия, то есть та самая, где всё сломалось.

Поиск по временному окну внутри лога:
```sh
grep -nE "^\[ *10[5-9][0-9]\." ~/.local/share/xorg/Xorg.0.log.old
```
Xorg ставит в начало строки время в секундах с момента запуска сервера — `[  1092.325]`.
Чтобы перевести в реальное время: узнать время старта X и прибавить.
`-n` показывает номера строк, чтобы потом вернуться к нужному месту.

Префиксы в логе Xorg:
- `(II)` — информация, `(WW)` — предупреждение, `(EE)` — **ошибка, ищи это первым**
- `(**)` — значение из конфига, `(==)` — значение по умолчанию

## Шаг 8. Когда именно что-то изменилось

```sh
ls -la --time-style=full-iso /etc/systemd/system/systemd-suspend.service.wants/
```

`systemctl enable` — это создание символьной ссылки. Время создания ссылки = время
включения сервиса. Сопоставив его с временем события в журнале, можно точно сказать,
успела ли настройка подействовать до сбоя.

`--time-style=full-iso` даёт полную дату с секундами и долями вместо усечённого
формата по умолчанию.

## Итоговая цепочка вывода

1. Сервисы включены и **отработали** при том самом закрытии крышки (журнал `-b -1`)
   → перезагрузка ни при чём.
2. Скрипт сервиса выходит немедленно, т.к. нет `/proc/driver/nvidia/suspend` (чтение кода)
   → сервисы бесполезны на этом драйвере.
3. Файла нет из-за `NVreg_UseKernelSuspendNotifiers=1` из пакетного конфига
   (`/proc/driver/nvidia/params` + `/usr/lib/modprobe.d/`).
4. `PM: suspend exit` есть, WiFi/NVMe/USB восстановились, ошибок `NVRM` нет
   → система просыпается полностью, ломается **только вывод изображения**.

Каждый шаг — факт из команды, а не предположение.

## Шпаргалка

```sh
# журнал
journalctl --list-boots --no-pager           # список загрузок
journalctl -b -1 --no-pager                  # предыдущая загрузка
journalctl -b -1 -k                          # только ядро
journalctl -b -1 -g "regex"                  # поиск
journalctl -b -1 --since "HH:MM" --until "HH:MM"
journalctl -f                                # следить в реальном времени
journalctl -u имя.service -b                 # по конкретному юниту

# systemd
systemctl is-enabled/is-active юнит
systemctl status юнит --no-pager
systemctl cat юнит                           # unit-файл + все drop-in'ы разом
systemd-analyze cat-config systemd/logind.conf   # итоговый конфиг со всеми /etc и /usr

# модули ядра
cat /proc/cmdline
grep -r "" /etc/modprobe.d/ /usr/lib/modprobe.d/
ls /sys/module/МОДУЛЬ/parameters/
lsmod | grep МОДУЛЬ

# железо и дисплеи
lspci -nn | grep -iE "vga|3d"
grep . /sys/class/drm/card*/status
cat /sys/class/backlight/*/actual_brightness
DISPLAY=:0 XAUTHORITY=$(pgrep -a Xorg | grep -oP '(?<=-auth )\S+') xrandr --query
```

## Что читать дальше (offline)

```sh
man journalctl        # раздел EXAMPLES внизу — сразу рабочие рецепты
man systemd.unit      # структура unit-файлов
man modprobe.d        # формат конфигов модулей
man 7 sysfs           # что вообще лежит в /sys
man 5 proc            # исчерпывающее описание /proc
```

Правило: у `man` внизу почти всегда есть `EXAMPLES` и `SEE ALSO`. Начинай с них,
а не с чтения страницы сверху вниз.
